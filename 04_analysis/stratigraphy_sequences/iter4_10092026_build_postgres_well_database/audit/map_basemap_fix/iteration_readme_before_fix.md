# Iteration 4: local PostgreSQL well database

**Status: Complete.** October 9, 2026, America/Los_Angeles. A storage migration of iteration 2's working release plus iteration 3's read-only audit and earlier history. No geological values, well selections, or height references were corrected.

Open the [interactive database map](evidence/maps/well_database_map.html). It contains all 7,402 original well IDs, with the current 332 working wells selected by default. Search for a well and select its point or list entry to see full stratigraphy, lithology, findings, ground-height evidence, iteration membership, and duplicate-survivor links. Archived wells keep their own observations and metadata.

## Database and backup

The live PostgreSQL/PostGIS service is `boardman-stratigraphy-db` in Docker Desktop. Its dedicated named volume is `boardman_stratigraphy_pgdata`. Windows client connection: `127.0.0.1:55432`, database `boardman`, username `boardman_admin`. Private credentials are in the ignored `../database/runtime/connection.json` file; they are not included in this iteration or Git.

The frozen [database backup](outputs/boardman.dump) contains the schema, records, relationships, and compressed original source files. [Shared tools v001](../database/versions/v001/README.md) explain startup, queries, backups, map regeneration, and restore. The exact image digest and implementation hashes are recorded in the iteration manifest.

The map is a portable HTML snapshot, generated by PostgreSQL queries with no CSV reads. Leaflet is embedded locally. Points, metric scale, controls, and details work without internet or a running database. The optional USGS background requires internet. Editing the database does not automatically refresh an existing map.

Every CSV field is preserved in `source_records.raw_values`, with stable source-hash/record identity. Original files themselves are stored losslessly in `source_files`, including earlier reports, audit outputs, maps, scripts, manifests, and cached ground-height pages. They can be reconstructed and verified against their SHA-256. Paths in historical documents remain historical references; data are stored inside PostgreSQL rather than fetched from CSVs.

All gaps, overlaps, deeper-than-completion records, and the zero-thickness lithology row remain. ## Continuing the workflow

Use `boardman.working_wells` and `boardman.working_intervals` as the working dataset. The accepted iteration 2 values are unchanged. Original data remain in iterations 0–2 and the database.

Later iterations reference shared `database/versions/v001` rather than copying the infrastructure. When shared tools change, create a new immutable version directory. Each completed iteration saves its own backup, maps, decisions, and checks. Future corrections insert new versions and membership records; historical rows reject UPDATE/DELETE. The [data dictionary](../database/versions/v001/DATA_DICTIONARY.md) documents the rules and the v001 review-status limitations.

All height sources remain unadopted. Source horizontal and vertical references still need review before rigorous 3D modeling. Location geometry uses the existing longitude/latitude display assumption, explicitly marked unverified. No coordinate/elevation transformation or new well confidence score was introduced.

ArcGIS export is deferred. Stable IDs, scalar fields and `boardman.arcgis_wells` support a later file-geodatabase export and creation of Esri relationships; this PostgreSQL database is not itself an Esri geodatabase.
